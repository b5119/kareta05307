ISSUE 4 - Message Broadcast Before Database Persistence [CRITICAL]
File: /home/frank-bwalya/Desktop/kareta05307/server/src/jvmMain/kotlin/ru.gr05307/net/ConnectedClient.kt
Lines: 33-36

Current Code (UNSAFE):
  when (type) {
      InfoType.MESSAGE -> {
          val formatted = "$username: $payload"
          broadcast(InfoType.MESSAGE, formatted, exceptSelf = false)  // LINE 35: BROADCASTS FIRST
          chatMessageService.saveMessage(username!!, payload, InfoType.MESSAGE.name)  // LINE 36: SAVES AFTER
      }
  }

Problem:
  - Message is broadcast to all connected clients immediately
  - If database save fails, message is already visible but NOT persisted
  - Users see message that disappears on server restart
  - Inconsistency between client view and database state
  - DATA LOSS VULNERABILITY

Impact:
  - Users cannot trust message history
  - Database becomes out of sync with broadcasts
  - Failed persistence creates invisible errors

Recommended Fix:
  val currentUsername = username ?: return
  try {
      // SAVE FIRST
      val savedMsg = chatMessageService.saveMessage(currentUsername, payload, InfoType.MESSAGE.name)
      // ONLY broadcast if save succeeds
      broadcast(InfoType.MESSAGE, formatted, exceptSelf = false)
  } catch (e: Exception) {
      // Notify client of failure
      sendMessage(InfoType.ERROR, "Ошибка: Сообщение не было сохранено на сервере")
      logger.error("Message persistence failed: ${e.message}", e)
  }

Severity: CRITICAL - DATA INTEGRITY RISK


ISSUE 8 - Concurrent Access to Mutable Username Field [CRITICAL]
File: /home/frank-bwalya/Desktop/kareta05307/server/src/jvmMain/kotlin/ru.gr05307/net/ConnectedClient.kt
Lines: 28-46 (message processing loop), 20 (field declaration), 129-136 (username assignment)

Problem:
  - username field (Line 20) is mutable (var, not val)
  - Accessed from multiple threads without synchronization
  - Single-threaded message processing per client
  - But if broadcast() or other operations take time, another thread could modify username
  - Message could be saved with wrong username or null username

Current Code:
  private var username: String? = null  // LINE 20: Mutable, no synchronization
  
  // In handle() message loop:
  while (true) {
      val raw = communicator.receive() ?: break
      // ...
      when (type) {
          InfoType.MESSAGE -> {
              val formatted = "$username: $payload"  // Reads unprotected
              broadcast(InfoType.MESSAGE, formatted, exceptSelf = false)
              chatMessageService.saveMessage(username!!, payload, InfoType.MESSAGE.name)  // Reads again, may differ
          }
      }
  }

Impact:
  - Race condition: username could change between read and save
  - Could save message with different username than displayed
  - Thread safety violations

Recommended Fix:
  Option 1: Make immutable snapshot
    val currentUsername = username ?: return  // Snapshot at start of message processing
    val formatted = "$currentUsername: $payload"
    broadcast(InfoType.MESSAGE, formatted, exceptSelf = false)
    chatMessageService.saveMessage(currentUsername, payload, InfoType.MESSAGE.name)

Severity: CRITICAL - CONCURRENCY ISSUE

ISSUE 3 - String-Based Message Type (Stringly-Typed) [HIGH]
File: /home/frank-bwalya/Desktop/kareta05307/server/src/jvmMain/kotlin/ru.gr05307/database/ChatMessage.kt
Line: 20-21

Code:
  @Column(nullable = false)
  open var messageType: String,   // "MESSAGE", "INFORMATION", "WARNING", "ERROR"

Problem:
  - messageType stored as VARCHAR string in database
  - No database constraint to validate values
  - Invalid strings like "GARBAGE" or "TYPO" could be persisted
  - Unsafe conversion when displaying (Line 103-104 in ConnectedClient.kt):
    val infoType = runCatching { InfoType.valueOf(msg.messageType) }
        .getOrDefault(InfoType.MESSAGE)
  - Silently defaults to MESSAGE if invalid type found

Database Schema Issue:
  message_type VARCHAR(255) NOT NULL  -- No CHECK constraint or ENUM type

Recommended Fix:
  Option 1: Use JPA Enum
    @Enumerated(EnumType.STRING)
    open var messageType: InfoType

  Option 2: Use database CHECK constraint (if keeping String)
    @Column(nullable = false, columnDefinition = "VARCHAR(50) CHECK (message_type IN ('MESSAGE', 'INFORMATION', 'WARNING', 'ERROR', 'PRIVATE', 'USERLIST'))")

Severity: HIGH - TYPE SAFETY / DATA INTEGRITY
